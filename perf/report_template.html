ARIES Observe — network & resource load test

Run __GENERATED__ · local stack (main site :5000 → gateway :4000 → propagation :8000) plus Cloudflare tunnel · internal report, not part of the website

Each phase ran simulated visitors against the live servers while small probe requests measured how responsive every page stayed, and a sampler recorded CPU, memory, threads, sockets and network for every server process twice a second.

What's slowing things down

  1. CriticalThe visualizer WebSocket sends the entire satellite catalogue (~10 MB of JSON) to every viewer about once a second. That is ~45 Mbit/s per open visualizer tab, and every byte has to go up through the Cloudflare tunnel uncompressed (Cloudflare does not compress WebSocket frames). One viewer plus one portal download already pushed the uplink to ~110 Mbit/s and made the public landing page ~8× slower. This is the main reason the visualizer and the Access Portal hurt each other.
    Fix: send a compact binary/quantised frame (positions only, Float32 lat/lon/alt ≈ 400 KB for 33k sats) and send static metadata (name, NORAD id, orbit type) once on connect; enable permessage-deflate; lower the frame rate to what the globe actually needs (Cesium can interpolate between 2–5 s updates).
  2. CriticalThe radar page's /passes call is very expensive and blocks the whole propagation service. It runs ~2 million SGP4 steps in pure Python (≈1,500 candidates × 1,440 minutes) and takes ~6 s alone, 15–28 s with three radar tabs open. Because it runs in a thread inside the same Python process, it holds the GIL and starves everything else: /visible jumped from ~0.4 s to ~25 s and new visualizer connections waited 7–15 s for their first frame.
    Fix: cache passes per observer (they barely change in 10 s — recompute every few minutes), call it once on page load instead of every 10 s, vectorise with sgp4's SatrecArray/NumPy, and run it in a separate worker process so the GIL is never shared with live data.
  3. CriticalThe propagation service is already at ~90–110% CPU with no visitors. It re-propagates all ~33k satellites every second in Python on a single core while 51 other cores sit idle. Every request (WebSocket, /visible, /passes) queues behind that loop, which is why /visible takes 0.4–0.9 s even when idle.
    Fix: vectorised propagation with SatrecArray.sgp4() (typically 20–50× faster), pre-serialise the JSON frame once per tick instead of per client, and keep /visible as a NumPy mask over the same arrays.
  4. HighRadar polls /visible every second and gets ~430 KB of JSON each time. The gateway caches it for only 2 s per exact lat/lon. The radar only needs name, az, el and orbit type for the ~1,000 visible satellites.
    Fix: return a trimmed payload (≈10× smaller), poll every 2–5 s, and stop polling when the tab is hidden (document.visibilityState).
  5. HighPortal downloads have no bandwidth limit and share the same uplink. Locally one 1.6 GB FITS download streams at ~1.4 Gbit/s and pins the main Node process at ~200% CPU. Through the tunnel a single download takes most of the available uplink, so pages and visualizer frames queue behind it.
    Fix: throttle /local/download and /nas/download per connection (e.g. a token-bucket stream), cap concurrent downloads, and/or serve large files over a separate path (Cloudflare R2 or a signed direct link) so they don't compete with interactive traffic.
  6. MediumStatic assets are sent uncompressed and with max-age=0. The 4.3 MB visualizer bundle and 1.6 MB earth texture are re-validated on every visit and travel the tunnel uncompressed (Cloudflare compresses only at its edge, after the tunnel leg). Hashed files in /visualizer/assets/ can be cached for a year.
    Fix: add compression middleware to backend/server.js, serve /visualizer/assets with immutable, max-age=31536000, convert the earth texture to WebP/AVIF, and split Cesium out of the main bundle.
  7. OKMemory and host CPU are not a constraint. All five processes together use well under 1.5 GB of 128 GB, and the host averages under 10% CPU across 52 cores. The landing page and other static pages stay fast locally under every load. The slowness is design-bound (payload size, single-threaded Python, shared uplink), not hardware-bound.

How this was measured

Generated by perf/netbench.py (re-run any time, then perf/make_report.py). Visualizer viewers are real WebSocket clients on /visualizer-ws/global; radar viewers poll /visualizer-api/visible every 1 s and /visualizer-api/passes every 10 s, as SkyRadarPage.jsx does; portal downloads are authenticated /local/download streams of a 1.6 GB FITS file. Per-process network is approximated from socket write volume (write_chars), as per-PID packet accounting needs root. Phases 1–6 hit 127.0.0.1:5000 and so exclude the internet link; phases 7–8 use https://www.aries-ssa.com with deliberately light load (1 viewer + 1 download) so real visitors weren't disrupted.
